# Next Gates — after v0.4 profile-driven prospective foundation

v0.4 closes the immediate abstraction step after the natural historical transition: the retained Version-Bound Effect cases can be expressed through one development profile and differentially reproduce the legacy semantic outcomes without moving verdict authority out of the frozen v0.7 producer/consumer path.

Do **not** expand the scientific core merely to create a larger release number.

## Gate A — external timestamp, then open prospective screening

Publish the exact bytes of `protocols/PROSPECTIVE_CORPUS_0.1_PROTOCOL.json` before screening any Case 004 candidate. Record the public commit identity separately. Do not rewrite the locally sealed protocol in place.

The screening gate remains closed until this is complete.

## Gate B — Prospective Corpus 0.1

Enroll the first 8 eligible units under the frozen protocol. Preserve `PRESERVED`, `CONSEQUENCE_REGRESSION`, `INCOMPLETE_ASSURANCE`, integrity failures, and null findings without outcome-driven replacement.

Required design properties include:

- at least 4 independent organizations;
- at least 3 carrier/mechanism families;
- no more than 2 enrolled units from one organization;
- agent-facing and non-agent-specific strata;
- known-bug hunting prohibited as a selection rationale;
- every screened rejection and enrolled result recorded.

## Gate C — acquisition-friction evidence

For every prospective unit, record the manual effort needed for operation selection, source-semantic reconstruction, boundary definition, evidence acquisition, version-binding discovery, envelope/adapter authoring, human correction, and verification runtime.

Automate only repeated high-confidence work demonstrated by this ledger. Do not build a generic semantic parser before the corpus shows which authoring steps actually repeat.

## Gate D — narrow acquisition hardening

Improve `risu init --profile version-bound-effect` only where the prospective friction ledger supports it. The authoring layer may propose candidate artifacts, but human acceptance remains required and the frozen core remains the only verdict authority.

## Gate E — independent use

Distinguish two evidence levels:

1. **Independent reproduction:** another person reruns a RISU-authored case.
2. **Independent authorship:** another person selects and authors a projection case using the method.

The second is the stronger transferability milestone.

## Gate F — layered comparative study

After a prospective corpus exists, run the same selected transitions through relevant interface/schema/security tooling and report which layer characterizes which change. Do not use tools addressing different questions as straw-man competitors.

## Gate G — native developer consumption

Only after the prospective workflow stabilizes, add developer-native output such as SARIF/source annotations, caching, and baseline comparison. Avoid a hosted dashboard merely to create visual polish.

## Gate H — portable attestation

Wrap the existing certificate payload in established attestation/signing infrastructure when results need to travel between systems. Do not invent a proprietary cryptographic scheme.

## Gate I — second semantic profile

Create a second consequence profile only if prospective evidence repeatedly exposes another carrier-neutral primitive. Do not preselect authority, idempotency, transactionality, or failure semantics merely because they are theoretically interesting.

## Gate J — verification graph / control plane

A result registry or `can-ship` style control plane becomes justified only when real users have enough certificates, revisions, environments, and release decisions that lifecycle management itself becomes a demonstrated problem.

## Explicit anti-goals

- no v0.8 core work without an empirical defect in the frozen method;
- no result quota or failure hunting in Corpus 0.1;
- no generic MCP security scanner;
- no LLM-issued `PRESERVED` verdict;
- no custom signing protocol;
- no premature “Consequential Action ABI v1”;
- no SaaS/dashboard before repeated external workflow need.
